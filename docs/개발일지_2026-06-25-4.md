## 변경 사항

### 1. DB 스키마 변경 (`supabase/migrations/20260625000001_payment_section.sql`)

**배경**  
기존 `payment_schedules` 테이블은 결제 데이터만 저장하는 구조였음. 환불 데이터를 별도 테이블 없이 같은 테이블에서 관리하기 위해 `section` 컬럼 추가.

**변경 내용**
```sql
-- section 컬럼 추가 (기존 데이터는 자동으로 'PAYMENT' 처리)
ALTER TABLE payment_schedules
  ADD COLUMN IF NOT EXISTS section text NOT NULL DEFAULT 'PAYMENT';

ALTER TABLE payment_schedules
  ADD CONSTRAINT payment_schedules_section_check
  CHECK (section IN ('PAYMENT', 'REFUND'));

-- 기존 UNIQUE(voyage_id, category, payment_type) 제거
-- section 포함 새 UNIQUE 제약으로 교체
ALTER TABLE payment_schedules
  DROP CONSTRAINT IF EXISTS payment_schedules_voyage_id_category_payment_type_key;

ALTER TABLE payment_schedules
  ADD CONSTRAINT payment_schedules_voyage_id_category_payment_type_section_key
  UNIQUE (voyage_id, category, payment_type, section);
```

- 기존 데이터는 `DEFAULT 'PAYMENT'`로 자동 마이그레이션되어 데이터 손실 없음
- 동일 행사·카테고리·결제유형에 대해 PAYMENT와 REFUND를 각각 독립적으로 저장 가능

## 기술 포인트

### 단일 테이블로 결제/환불 분리 관리
별도 테이블을 신설하지 않고 `section` 컬럼 하나로 결제와 환불을 구분. UNIQUE 제약에 section을 포함시켜 같은 행사·카테고리·결제유형에 대해 두 레코드(PAYMENT, REFUND)가 공존할 수 있도록 설계.

### DraftKey에 컨텍스트 인코딩
`section_category_payment_type` 형식의 복합 키로 두 그리드의 상태를 단일 `drafts` Record에 통합 관리. 렌더링 시 섹션별로 키를 필터링할 필요 없이 키 자체에 섹션 정보가 포함되어 있으므로 상태 충돌 없음.

### 기존 데이터 무손실 마이그레이션
`DEFAULT 'PAYMENT'` 설정으로 ALTER TABLE 시점에 모든 기존 행이 자동으로 결제 섹션으로 분류됨. 앱 코드에서도 `s.section ?? 'PAYMENT'` 폴백 처리로 구버전 데이터 호환성 보장.
