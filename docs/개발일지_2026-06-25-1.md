## 변경 사항

### 1. 결제 탭 N차 데포짓 동적 추가 (`src/components/voyages/tabs/PaymentTab.tsx`)

**배경**  
기존 결제 탭은 `1차 데포짓 / 2차 데포짓 / 잔금` 3개 행으로 고정되어 있어, 3차 이상 데포짓이 발생하는 행사에 대응할 수 없었음.

**변경 내용**  
- 테이블 하단에 **데포짓 추가** 버튼 추가 — 클릭할수록 `3차 데포짓`, `4차 데포짓` … 행이 잔금 위에 삽입됨
- `PAYMENT_TYPES` 고정 배열 제거 → `extraDepositCount` 상태 기반 동적 `paymentTypes` useMemo로 대체
- `PAYMENT_TYPE_LABEL` Record 제거 → `paymentTypeLabel(pt: string)` 함수로 대체

```typescript
// 레이블 함수 — 기존 값 + DEPOSIT_N 패턴 모두 처리
function paymentTypeLabel(pt: string): string {
  if (pt === 'DEPOSIT_1ST') return '1차 데포짓'
  if (pt === 'DEPOSIT_2ND') return '2차 데포짓'
  if (pt === 'BALANCE') return '잔금'
  const m = pt.match(/^DEPOSIT_(\d+)$/)
  if (m) return `${m[1]}차 데포짓`
  return pt
}

// 동적 paymentTypes
const paymentTypes = useMemo((): string[] => {
  const rows: string[] = ['DEPOSIT_1ST', 'DEPOSIT_2ND']
  for (let i = 3; i <= 2 + extraDepositCount; i++) rows.push(`DEPOSIT_${i}`)
  rows.push('BALANCE')
  return rows
}, [extraDepositCount])
```

**DB 스키마 변경** (`supabase/migrations/20260625000000_payment_extra_deposits.sql`)  
`payment_type` CHECK 제약을 기존 ENUM 목록에서 정규식 패턴 포함으로 완화.

```sql
ALTER TABLE payment_schedules
  DROP CONSTRAINT IF EXISTS payment_schedules_payment_type_check;

ALTER TABLE payment_schedules
  ADD CONSTRAINT payment_schedules_payment_type_check CHECK (
    payment_type IN ('DEPOSIT_1ST', 'DEPOSIT_2ND', 'BALANCE')
    OR payment_type ~ '^DEPOSIT_[0-9]+$'
  );
```

**새로고침 복원 로직**  
useEffect 내에서 DB schedules에 `DEPOSIT_\d+` 패턴 값이 있으면 `extraDepositCount`를 자동 계산해 행 복원.

```typescript
const extraNums = schedules
  .map(s => s.payment_type)
  .filter(pt => /^DEPOSIT_(\d+)$/.test(pt))
  .map(pt => parseInt(pt.replace('DEPOSIT_', ''), 10))
const newExtraCount = extraNums.length > 0 ? Math.max(...extraNums) - 2 : 0
setExtraDepositCount(Math.max(0, newExtraCount))
```

**DraftKey 파싱 호환성**  
기존 `${category}_${payment_type}` DraftKey를 `key.split('_')` → `[cat, ...rest]` → `rest.join('_')`으로 파싱하는 로직이 `DEPOSIT_3`, `DEPOSIT_4` 등 숫자형 타입에도 그대로 동작.

| DraftKey | cat | rest.join('_') |
|---|---|---|
| `CRUISE_DEPOSIT_1ST` | CRUISE | DEPOSIT_1ST |
| `HOTEL_DEPOSIT_3` | HOTEL | DEPOSIT_3 |
| `FLIGHT_BALANCE` | FLIGHT | BALANCE |

### 2. 항공 탭 행사명 아래 경유 항공사 표시 (`src/components/voyages/tabs/FlightsTab.tsx`)

**배경**  
항공 탭 테이블에 개별 항공편 정보는 있지만 해당 편이 어느 행사의 어떤 항공사 노선인지 한눈에 파악하기 어려웠음.

**변경 내용**  
- `fetchAllVoyageFlights` select에 `airline, airline_return` 추가
- 행사명 셀 아래에 `EK / EK` 형태 서브라벨 표시

```typescript
// voyageFlights.ts — select 확장
.select('*, voyages(region, departure_date, airline, airline_return)')

// FlightsTab.tsx — 헬퍼 함수
function airlineLabel(v: { airline?: string | null; airline_return?: string | null } | null): string | null {
  const a = v?.airline?.trim() || null
  const b = v?.airline_return?.trim() || null
  if (!a && !b) return null
  if (a && b) return `${a} / ${b}`
  return a ?? b
}
```

```tsx

      {airlineLabel(r.voyages)}
    </span>
  )}
</span>
```

## 기술 포인트

### PaymentType을 string으로 확장
`PaymentType = 'DEPOSIT_1ST' | 'DEPOSIT_2ND' | 'BALANCE'` 유니온은 동적 값(`DEPOSIT_3` 등)을 허용할 수 없어 `string`으로 변경. 런타임 안전성은 DB CHECK 제약과 `paymentTypeLabel` 함수에서 담보.

### DB CHECK 제약 vs TypeScript 유니온 타입
고정 값 목록을 DB 제약으로 강제하면, TypeScript 타입을 넓혀도 실제 잘못된 값이 DB에 들어가는 것을 방지할 수 있다. 제약을 정규식 패턴(`~ '^DEPOSIT_[0-9]+$'`)으로 설계하면 애플리케이션 코드 변경 없이 N번째 데포짓을 유연하게 지원 가능.
